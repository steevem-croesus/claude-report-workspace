Partie 1 — Pourquoi03

Le problème

Un seul champ de rapport traverse 5 codebases

CroesusServer
C++→ ReportServer
C++→ ReportFoundations
C#→ ReportManagerApi
C# .NET 8→ pf-web
Angular 21 + NX

Là où l'IA « ad hoc » dérape

  • elle devine le mauvais repo ;
  • elle invente des exigences que le ticket n'a jamais énoncées ;
  • elle écrit du code avant de comprendre le flux existant ;
  • elle ship un port plausible-mais-faux d'un calcul de dates C++ subtil.

Et le contexte aggrave tout

  • 3 langages, chacun ses conventions ;
  • une branche + une MR par repo (règles git de l'org) ;
  • un ordre de pipeline fixe : C++ → C#/API → UI ;
  • de la logique financière et de dates où « à peu près » = bug en production.
La réponse en une phrase : rendre le travail lisible et réversible — chaque étape produit un artefact nommé qu'on peut lire ; chaque étape risquée attend une approbation humaine.
Partie 1 — Pourquoi04

Philosophie de conception

Cinq idées, et tout le reste en découle

1

La forme du process = le type de travail

Un bug a besoin d'une repro. Un refactor, de tests de caractérisation. Un spike, d'un timebox. Le workflow est le garde-fou.

2

Un artefact par phase, sur disque

Le raisonnement devient inspectable, survit aux sessions, et ne pollue pas les repos produit.

3

Les gates aux moments irréversibles

Lire et planifier est réversible. Écrire — et surtout shipper — ne l'est pas. Deux arrêts universels.

4

Des agents étroits, un seul métier

Un relecteur laconique qui ne fait que relire relit mieux qu'un généraliste qui a aussi écrit le code.

5

Déférer à l'autorité locale

Les skills défèrent aux conventions ; les agents au CLAUDE.md du repo. Une seule source de vérité par sujet.

Ce que ça vous apporte

Un fix de bug a un vrai test de régression. Un refactor n'a pas changé le comportement. Vous voyez le plan — risques, estimation, note honnête — avant que le code existe.

Ce que ce n'est délibérément pas

Pas autonome. C'est gaté à dessein : ça demande plutôt que de deviner. Et ce n'est pas un remplacement de code-fleet — ça interopère avec.

Partie 2 — Le repo07

Rappel produit

Le flux de génération d'un rapport

1
L'utilisateur demande un rapport depuis pf-web (ou l'ancien ReportWebClient).
2
POST /api/v1/reports sur ReportManagerApi crée la demande : payload poussé sur une file SQS, ligne de statut écrite dans B_RPT_BATCH_GEN_REQUEST.
3
Un worker batch dépile et génère via la logique ReportFoundations, qui interroge le Frameworkserver (CroesusServer) sur le port 8999 pour les données de portefeuille.
4
Le fichier atterrit dans un bucket S3 — le frontend le télécharge via GET /api/v1/reports/{generationId}.

Convention de nommage vserver

File {vserver}-reports-sqs · bucket {vserver}-reports-bucket.

Pourquoi c'est dans le deck

C'est l'ordre du pipeline que les workflows imposent en phase build : analyse C++ → C#/API → UI Angular. Jamais l'inverse.

Pourquoi ça compte

Inspectable — on lit le plan avant qu'une ligne existe, et la review avant d'approuver le ship.
Reprenable — la trace est toujours là la semaine suivante.
Propre — rien du process ne fuit dans les repos produit.

Règle non négociable

Toute revue de code produit un fichier, pas seulement une réponse en chat — review-code.md écrit avant le résumé. Le chat est volatile ; le fichier est ce qu'on relit, ce qu'on coche, et ce qui alimente la description de MR.

Partie 4 — Protocole14

Gates

Un humain aux moments irréversibles

À chaque gate, l'orchestrateur s'arrête et interroge via AskUserQuestion : « Approuver, demander des changements, ou annuler ? » Un gate n'est jamais franchi automatiquement.

✓ approve

On passe à la phase suivante. C'est tout.

↻ changes

Le retour est écrit mot pour mot dans _signals/revision-request.md, l'agent de la phase est redispatché (il relit son artefact + la demande), puis on revient au même gate avec l'artefact révisé.

✕ cancel

Le workflow s'arrête. Les artefacts restent sur disque — on peut reprendre plus tard.

Les deux gates universels

Gate de plan — après plan.md, avant qu'une ligne de code existe.
Gate de code — après build-summary.md + review-code.md, avant le ship.

Plafond de boucle

La boucle build ↔ review est plafonnée à 3 itérations. Au-delà, on s'arrête et on signale les problèmes restants plutôt que de tourner en rond.

Partie 4 — Protocole15

La barre de build

On ne builde que depuis un plan ready noté A ou S

plan.md porte un en-tête auto-attribué : **Status:** <draft|ready> · **Grade:** <F|D|C|B|A|S> — échelle F < D < C < B < A < S, barème détenu par agents/planner.md.

F

plan absent / faux

D

lacunes majeures

C

incomplet

B

presque — pas approuvable

A

barre atteinte

S

exemplaire

Sous la barre

Le gate n'offre pas approve. On fait ressortir la note + le pourquoi (questions ouvertes bloquantes, points de décision needs-user) et on route vers changes.

Au-dessus de la barre

L'utilisateur obtient le choix normal approve / changes / cancel. Une note qualifiante déverrouille le gate — elle ne le franchit pas.

Passer outre

C'est permis (petit changement délibéré), mais consigné dans revision-request.md pour rester auditable. Sans passage outre explicite, la barre tient.

Le contre-pouvoir : le reviewer en mode plan vérifie explicitement si le Grade + Status auto-attribués sont honnêtes. Un plan sur-noté ou marqué ready à tort est un must-fix — parce que toute la barre en dépend.
Partie 4 — Protocole16

Protocole HALT

Un agent qui ne sait pas demande — il ne devine pas

Le bloc qu'un agent renvoie

HALT: need user decision
Reason:           <pourquoi il ne peut pas continuer>
Question:         <la question précise>
Proposed default: <sa recommandation>
State:            <l'avancement, pour reprendre>

N'importe quel agent producteur peut s'arrêter en cours d'exécution : planner, implementer, cpp-to-csharp-porter, context-gatherer, investigator.

Ce que fait l'orchestrateur

1. Fait remonter la question via AskUserQuestion.
2. Écrit la réponse dans _signals/resume.<agent>.md.
3. Redispatche l'agent, qui reprend où il en était.

Plafond

3 allers-retours HALT par agent. Au-delà : on procède avec la valeur par défaut énoncée, ou on s'arrête avec un message clair.

Pourquoi c'est mieux qu'une question défensive

Un HALT ne se déclenche que sur une véritable bifurcation — pas de « es-tu sûr ? ». Le coût d'une interruption est payé là où deviner coûterait un port financier faux.

Partie 4 — Protocole17

Garde-fous

Ce qui s'applique à chaque agent, chaque phase

Interdits de l'organisation

Jamais les CLI interdites : aws, terraform/tofu, ni leurs wrappers (assume, granted). ReportManagerApi utilise AWS uniquement via le SDK et la config — jamais la CLI.

Read-only veut dire read-only

explorer, investigator, learning-guide, reviewer, retrospective, report-analyst, migration-reviewer, migration-validator n'éditent jamais de code. Le context-gatherer est aussi read-only sur Jira/GitHub : il ne commente ni ne transitionne un ticket.

Règles de branche & push

Brancher depuis une réf protégée (main, develop, release/*, support/*) toujours avec --no-track :
git switch -c <nom> --no-track origin/develop
Premier push : git push -u origin <branche> — jamais un git push nu (il pourrait fast-forwarder la branche protégée).

Autorité locale & commits

Le CLAUDE.md/copilot-instructions.md du repo cible prime sur tout conseil générique. Les agents git add-stagent les nouveaux fichiers mais ne committent pas : le commit est l'étape de ship, gatée.

Ne jamais fabriquer : si Jira ou GitHub est injoignable, le workflow avance sur les preuves locales et le signale. Aucun agent n'invente le contenu d'un ticket, ni un résultat de test, ni un Closes non vérifiable.

Partie 5 — Agents20

Zoom

Trois agents qui portent le plus de valeur

explorer — l'heuristique qui sauve

Quand une feature lit de la config « default »/setup, il ne s'arrête pas au helper évident : il trace aussi le chemin de découverte repository / Flex scenario (I*Repository.BuildScenarioData, Get*SetupConfig) — parce que le chemin de génération résout souvent les données via un scenario que le helper côté query masque.

Il signale aussi les surfaces partagées (interface à rendre générique, classe de base à extraire) quand une feature ajoute un flow à côté d'un flow existant.

reviewer — laconique et adversarial

Pas d'éloges, pas de résumé, pas de scope creep. Une ligne par constat :

repo/path:line : 🔴/🟡/🟢 problème. correctif.

Sévérités 🔴 must-fix / 🟡 should-fix / 🟢 consider, une ligne Don't miss, et un verdict : clean / should-fix only / must-fix present.

Il peut builder et lancer des tests pour vérifier un constat — sans muter le code.

cpp-to-csharp-porter — fidélité d'abord

Suit la recette de copilot-instructions.md à la lettre. Les indices de mapping :

  • PREF_ → IPreferencesRepository
  • PARAM_ → IReportCommandAndQueryContextRepository
  • dates → IParameterDateValueService / IDateTimeService

Il rapporte tout comportement C++ qu'il n'a pas pu reproduire fidèlement, et HALT plutôt que de deviner une logique financière ou de dates.

Le mode migration de /feature

Quand la feature est une migration de rapport, /feature bascule en mode migration (§1a) : les gates restent, mais les workers de phase sont ces agents — report-analyst (explore+plan) → backend-migrator puis frontend-migrator (build) → migration-reviewer + migration-validator (review). La spec de l'analyste est le plan.

Livrables & entrées

Tous les livrables sous .work/{slug}/ (analysis, logs, review, PDF, state.json) — jamais sous docs/reports/. Les entrées globales partagées restent sous docs/ : fields.csv (liste maître des paramètres) et template_ids.csv.

Si le plan est sous la barre

approve n'est pas proposé. On voit la note, les bloqueurs, et les points de décision needs-user — qui sont d'abord résolus via AskUserQuestion, puis le planner est redispatché jusqu'à ready + A/S.

Si vous demandez des changements

Votre retour est écrit mot pour mot dans _signals/revision-request.md. Le planner le relit avec son plan précédent et revient au même gate.

Ce que ça achète

Vous corrigez la conception au moment où c'est gratuit. Une mauvaise décision d'architecture attrapée ici coûte une phrase ; attrapée au gate de code, elle coûte un rebuild complet.

Build, review, et la boucle

6
Build — un builder par tranche de repo
Pour chaque sous-section #### <repo> du plan, dans l'ordre du pipeline (analyse C++ → C#/API → UI Angular) : cpp-to-csharp-porter si l'étape est un port de value-provider, implementer sinon. Chacun respecte le CLAUDE.md du repo cible, écrit les tests dans le tier/style du repo, et builde puis exécute ses tests avant de retourner — en rapportant la sortie réelle des commandes. Résultat ∈ ok / tests-failed / build-failed. Les builders git add-stagent mais ne commitent pas.
→ build-summary.md  ·  fichiers par repo · tests ajoutés · commandes exactes + résultats · déviations

Sur le diff de travail : bugs de correction, violations de layering, tests faibles ou manquants, dérive de contrat cross-repo, fidélité C++→C#. Une ligne par constat, sévérité taguée, un verdict.
→ review-code.md

GATE de code
L'orchestrateur présente le verdict de review + le résultat du build, puis demande approuver / changements / annuler.
↻ changements — ou un must-fix présent → les constats sont écrits dans _signals/revision-request.md et on reboucle en phase 6, le builder rebuildant face à la review. Plafond : 3 itérations build ↔ review, ensuite on s'arrête et on signale ce qui reste.

Partie 6 — Jira → MR28

Phase 9 — le ship

Une branche, un commit, une MR par repo

Optionnel et gaté : l'orchestrateur demande s'il faut shipper. Si non, on saute entièrement. Si oui, par repo touché — il n'y a pas de repo racine partagé.

Les étapes, dans l'ordre

# 1 · brancher depuis la réf protégée
git switch -c feature/RPT-19587-… --no-track origin/develop

# 2 · committer (skill git-commit)
git add … && git commit

# 3 · premier push, destination explicite
git push -u origin feature/RPT-19587-…

# 4 · ouvrir la MR (skill merge-request)
gh pr create --base develop --head … --body-file … -d

Les refus (garde-fous bloquants)

Jamais de MR depuis une branche protégée ; jamais depuis le root d'outillage (pas de remote → une PR n'y a aucun sens) ; jamais une MR qui couvre deux repos ; jamais un premier push nu. Si l'upstream pointe une réf protégée → git branch --unset-upstream avant de pousser.

Cross-repo = MR séparées, cross-liées

Un changement C#/API + Angular devient deux MR, une par repo — annoncées comme telles, créées chacune, puis liées l'une à l'autre dans leurs descriptions.

Base : Gitflow

develop par défaut ; main/master seulement pour hotfix/* et release/*. Toute autre base est confirmée avec vous.

Partie 6 — Jira → MR29

La MR

Un titre et un corps sur lesquels un reviewer peut agir

Le corps, en français, structuré

## Résumé
1–3 phrases : ce que ça livre et pourquoi.

## Changements
- <zone/fichier> : ce qui change

## Tests
ce qui a été lancé et le résultat — ou honnêtement « non lancé ».

## Changements incompatibles
API/DTO/contrat + répercussion ReportFoundations — ou « Aucun ».

## Tickets liés
Closes RPT-19587

## Notes de revue
les 1–3 endroits à regarder en premier.

Le titre

Conventional Commits, impératif, ≤ 72 car., sans point final : <type>(<scope>): <ce que ça fait>. Sur un repo squash-mergé (pf-web) le titre devient le sujet du commit de squash — donc il doit être un sujet CC propre.

La matière première

Le corps synthétise — il ne relit pas la liste des commits : git log <base>..HEAD pour les intentions, git diff <base>...HEAD pour ce qui a réellement changé, et .work/<slug>/context.md pour le pourquoi.

Deux règles dures

Jamais de résultat de test inventé, ni de Closes non vérifiable.
Jamais de merge : ouvrir la MR est là où ça s'arrête. Pas de gh pr merge, pas d'approbation. Merger est une décision humaine.

Partie 6 — Jira → MR30

Phase 10

La rétrospective — pour que la connaissance ne s'évapore pas

Ce que produit retrospective

  • ce qui a été shippé ;
  • plan vs réalité — où l'estimation a dérivé et pourquoi ;
  • ce qui s'est bien / mal passé, et ce qui a surpris ;
  • la classe de cause racine (bugs uniquement) — pour attraper les bugs similaires plus tôt ;
  • des suivis concrets ;
  • 1–4 apprentissages durables proposés : entrées de mémoire + éditions doc/CLAUDE.md, sous forme de checklist.
→ retro.md

Le garde-fou qui compte

Elle n'écrit jamais la mémoire elle-même et ne modifie pas la doc. Elle fait remonter la checklist pour votre approbation. C'est vous qui décidez ce qui devient une règle durable.

L'effet cumulatif

C'est ce qui fait que le workspace s'améliore : chaque migration, chaque bug de tracing, chaque piège de convention approuvé devient une mémoire que le prochain workflow lit automatiquement — et donc une erreur qui ne se reproduit pas.

Et le résumé final

L'orchestrateur clôt avec : ce qui a été construit, la note du plan, le résultat build/review, les URL des MR, et les apprentissages en attente d'approbation.

Ce que bug et refactor changent

/bug — deux phases ajoutées avant le plan

2
Reproduce
orchestrateur (+ explorer pour localiser) → un test en échec ou une repro documentée.
3
Diagnose — investigator
cadrer → preuves (code, git log/blame/log -S, tickets, logs) → hypothèses → vérification adversariale (essayer de réfuter l'hypothèse principale ; distinguer le déclencheur de la cause racine) → conclusion + confiance.

3
Characterize
orchestrateur + implementer → un filet de sécurité de tests capturant le comportement actuel, écrit avant d'y toucher ; les lacunes sont notées.
5

chaque étape vérifiée individuellement — build + tests verts après chacune.

La règle distinctive : le comportement ne doit pas changer. Le plan liste des étapes ordonnées et préservant le comportement, avec les surfaces de changement cassant explicites ; un refactor de ReportFoundations doit signaler chaque consommateur en aval. Récapitulatif

Cinq choses à retenir

1 · Le workflow est le garde-fou

Choisir bug plutôt que « corrige-moi ça » impose une repro et un test de régression. C'est la décision la plus rentable de la session.

2 · Le plan est lu avant que le code existe

Et il ne passe le gate que ready + noté A/S — avec un relecteur qui vérifie que la note est honnête.

3 · Deux arrêts, et seulement deux

Après le plan, après le build+review. Gratuits nulle part ailleurs — et jamais franchis automatiquement.

4 · Chaque phase laisse un fichier

.work/<slug>/ : lisible, reprenable la semaine suivante, et hors des repos produit.

5 · Le ship respecte l'org, repo par repo

--no-track, push -u, une MR par repo, un corps qu'un reviewer peut actionner — et jamais de merge automatique.
